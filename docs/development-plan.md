# 像素餐厅经营游戏：分阶段开发计划

版本：v0.1  
编写日期：2026-09-23  
文档定位：从零开始制作首个可玩版本的设计与开发执行计划

## 1. 项目目标与基本假设

### 1.1 一句话玩法

玩家通过亲自劳动和雇佣员工完成餐厅运营，赚取利润，优化布局与分工，逐步扩建餐厅。

### 1.2 核心体验

游戏应让玩家经历三个变化：

1. **亲自经营：** 理解做菜、上菜、收盘和清洁之间的关系。
2. **学会分工：** 雇佣第一位员工，把部分工作交出去，在忙碌时主动补位。
3. **经营成长：** 根据营业结果决定采购、设备升级和扩建，让餐厅接待更多顾客。

首个版本的核心验证问题是：雇佣员工后，玩家是否明显感到负担减轻，并获得新的经营选择？

### 1.3 开发假设

以下是便于启动开发的暂定选择，可以在原型阶段调整：

| 项目 | 暂定方案 |
|---|---|
| 引擎 | Godot 4.x；启动项目时选择并固定一个稳定版本 |
| 开发语言 | GDScript |
| 平台 | 优先电脑端，先验证键盘操作 |
| 游戏形式 | 单人、本地存档、俯视角 2D |
| 美术 | 像素风；先用占位图验证玩法 |
| 地图 | 固定小店，家具按格子摆放，后续解锁固定扩建区 |
| 移动 | 角色自由移动；员工按格子路径规划，向操作位置移动 |
| 游戏节奏 | 偏轻松经营，营业高峰带来适度压力 |
| 人员预算 | 按 1 名全职开发者估算，不假设已有成熟代码或美术资产 |

本计划中的数量、时长和经济参数都是原型起点，不是最终平衡结果。

## 2. 第一版范围与完成定义

### 2.1 必须包含的内容

| 类别 | 首个可玩版本内容 |
|---|---|
| 餐厅 | 一个初始店面，约 4 张桌子，一块固定扩建区 |
| 主角 | 移动、交互、搬运、全部实操工作和管理操作 |
| 实操 | 制作食物、上菜、收盘、清洁地面 |
| 员工 | 同时最多雇佣 1 名；支持四类实操任务和优先级设置 |
| 顾客 | 一种基础顾客行为；外观可有少量变体 |
| 菜品 | 2 道菜，共用一种短时制作小游戏 |
| 家具 | 餐桌座椅、烹饪台、出餐台、餐盘回收点 |
| 管理 | 采购、菜单开关、员工分工、家具摆放、设备升级 |
| 成长 | 至少一种设备升级，一次餐厅扩建 |
| 反馈 | 顾客耐心、评价原因、每日经营结算 |
| 存档 | 打烊结算后的本地存档与读取 |
| 新手引导 | 引导完成首桌服务、首次雇佣和查看结算 |

### 2.2 明确延后的内容

- 多人联机、云存档、移动端适配。
- 自由建墙、多楼层、多分店和室外开放世界。
- 外卖、供应商关系、贷款利息和复杂财务系统。
- 食材保鲜、洗碗机与餐具库存、复杂加工链。
- 员工性格、社交关系、排班、休息与情绪。
- 每道菜独立小游戏、大量菜谱和复杂烹饪组合。
- 天气、节日、随机灾害和大型剧情。

这些内容进入后续候选清单，不在首版开发中穿插实现。

### 2.3 首版完成定义

玩家可以从新档开始，连续经营多个营业日，完成采购、服务、结算、首次雇佣、设备升级和首次扩建；保存后重新进入游戏能够继续经营。过程中没有阻断经营的任务卡死、金币重复结算、库存负数或无法恢复的资金死局。

## 3. 统一玩法规则

### 3.1 每日循环

```text
开店前：采购 → 调整菜单 → 布置家具 → 安排员工
    ↓
营业中：接待 → 做菜 → 上菜 → 用餐付款 → 收盘清洁
    ↓
停止入店：处理剩余顾客与工作
    ↓
打烊后：工资结算 → 查看经营报告 → 升级扩建 → 保存
    ↓
下一营业日
```

- 开店前和打烊后不消耗营业时间。
- 营业期间禁止移动、出售家具；可调整员工工作优先级。
- 暂停菜单暂停经营时间；烹饪小游戏期间餐厅继续运行。
- 营业结束后停止生成新顾客，现有顾客继续完成服务或因超时离开。
- 设置收尾时限。超过时限后取消未完成订单、送走剩余顾客并清理关联任务，避免无限等待。
- 收尾时剩余脏桌、污渍由闭店清场处理并恢复初始状态；结算前明确显示这一过程，首版不额外收费。

### 3.2 顾客与订单

- 首版每张桌子只接待一个顾客单位，每位顾客只点一道菜，不做拼桌。
- 顾客入店时预留一张可用桌子；没有可用桌子则离开，首版不实现排队区。
- 入座后自动点单，玩家不需要执行额外的接单动作。
- 顾客只从开启且有可预留食材的菜品中选择；无可售菜品时离店，并给玩家缺货提示。
- 订单接受时预留食材，开工时实际扣除；开工前取消释放预留，开工后取消不返还食材。
- 等餐阶段消耗耐心；上菜后转入用餐，不再因等餐超时取消订单。
- 用餐结束自动付款并生成评价，首版不增加收银岗位。
- 顾客离开后桌子进入待收盘状态，收盘完成才能接待下一位顾客。

### 3.3 工作与搬运

| 工作 | 前置条件 | 完成结果 |
|---|---|---|
| 做菜 | 有有效订单、预留食材和可用烹饪台 | 生成与订单绑定的成品，放入出餐位置 |
| 上菜 | 成品已就绪，顾客仍在等待 | 食物送到对应桌子，顾客开始用餐 |
| 收盘 | 顾客已离店，桌上有餐盘 | 搬到回收点后桌子恢复可用 |
| 清洁 | 有尚未处理的地面污渍 | 移除污渍，改善环境状态 |

- 主角初期一次携带一个物品，不能同时端菜和拿餐盘。
- 食物绑定订单，首版不允许错误上菜；交互失败时显示原因。
- 员工领取任务后预留目标及必要物品，其他执行者不能重复领取。
- 默认不允许玩家抢走员工执行中的物品，界面显示“员工处理中”。后续可增加显式接手功能。
- 取消任务必须释放相关预留。已经搬起的物品需要放回、回收或丢弃，不能只删除任务引用。
- 首版不允许把物品随意扔到地上；提供出餐台放回和无效食物丢弃入口。
- 出餐位置有限。做菜开工前预留可用出餐位置，避免完成后无处放菜。
- 餐盘回收点首版容量无限，不实现后续洗碗流程。

### 3.4 制作小游戏

采用一种短时火候判定：玩家开始烹饪后，按时确认获得普通或优质成品。

- 失败也产出普通成品，首版不额外惩罚食材损失。
- 超时按普通结果完成，避免忘记操作导致工作台永久占用。
- 员工采用计时制作，产出普通品质，后续再扩展熟练度。
- 玩家表现只提供适度品质奖励，不设置只有手动操作才能制作的必需菜品。
- 中途退出交互时明确提示取消；按已开工规则处理食材，释放工作台和出餐位置。

### 3.5 布置和升级

- 家具有占地格子、操作格子和朝向。
- 放置前检查越界、重叠、入口连通和必要操作位置可达。
- 首版先支持移动已有家具与购买餐桌，出售和复杂旋转可按进度延后。
- 烹饪设备升级主要缩短制作时间；扩建主要增加可用面积和摆放空间。
- 增加餐桌不会自动提高厨房或员工效率，让玩家观察真实瓶颈。

## 4. 技术组织与数据约定

### 4.1 模块划分

| 模块 | 职责 | 不应承担的职责 |
|---|---|---|
| 营业流程 | 开店、营业、收尾、结算的阶段切换 | 具体角色移动 |
| 订单管理 | 订单状态、顾客关联、取消和完成 | 员工寻路 |
| 工作调度 | 生成任务、领取、预留、取消、失败恢复 | 顾客评价公式 |
| 库存管理 | 可用量、预留量、扣除和释放 | 直接修改金币 |
| 经营账本 | 收入、采购支出、工资、升级支出 | 操作场景家具 |
| 布局管理 | 家具位置、占地、操作格、可达性 | 决定顾客点什么菜 |
| 角色控制 | 主角输入、员工执行、顾客状态行为 | 独立复制结算规则 |
| 存档管理 | 数据版本、保存、读取和恢复默认值 | 保存临时节点引用 |

玩家与员工共用工作执行规则：开始前检查、占用资源、完成效果、取消清理。小游戏只是玩家完成做菜时的输入方式，不另做一套订单逻辑。

### 4.2 核心数据

| 数据 | 最小字段 |
|---|---|
| 菜品定义 | 标识、名称、售价、食材需求、基础耗时、品质加成 |
| 家具定义 | 标识、占地、操作位置、价格、工作类型、升级效果 |
| 订单 | 标识、顾客标识、桌子标识、菜品、状态、创建时间、食材预留 |
| 任务 | 标识、类型、目标标识、关联订单、状态、执行者、优先级、预留资源 |
| 员工 | 标识、工资、开启的工作类型、优先级 |
| 存档 | 版本、天数、金币、库存、菜单、家具位置、升级、员工、扩建状态 |

静态配置与运行状态分开存放；菜品、家具等可使用 Godot Resource 表达。界面通过事件更新显示，避免界面本身拥有金币或订单的权威数据。

### 4.3 状态约定

```text
订单：等待制作 → 制作中 → 待上菜 → 用餐中 → 已结算
                  任意允许取消的阶段 → 已取消

任务：等待领取 → 已领取 → 执行中 → 已完成
          ↑          ↓         ↓
          └── 可恢复失败 ──────┘
                     或 → 已取消

员工：空闲 → 选择任务 → 前往目标 → 执行 → 搬运/交付 → 空闲

桌子：可用 → 已预留 → 用餐服务中 → 待收盘 → 可用
```

可恢复失败需要有限重试和重新评估；不可达任务应暂时降低调度优先级并说明原因，不能每帧反复领取。

### 4.4 路径与碰撞策略

- 先依据家具占地建立可通行格子，角色走到家具操作位置才开始工作。
- 所有家具交互都使用操作位置，避免角色走向桌子中心。
- 初期角色之间不设阻挡行走的硬碰撞，先确保订单和调度稳定。
- 后续可增加轻量避让；狭窄通道与多角色拥堵单独评估，不在原型阶段追求真实人群模拟。
- 布置只在非营业阶段发生，确认布局后统一更新通行数据。

Godot 官方导航资料：<https://docs.godotengine.org/en/stable/tutorials/navigation/>。实际使用的接口以项目固定版本文档为准。

## 5. 阶段一：单人服务闭环

**目标：** 一个顾客能够完成一次完整消费，玩家能重复接待下一位顾客。

### 5.1 工作清单与顺序

1. 创建 Godot 项目、版本管理和基础场景；确定输入动作与暂停规则。
2. 制作占位餐厅：入口、地面、墙体、一张桌子、烹饪台、出餐台、回收点。
3. 实现主角移动、碰撞、朝向与附近目标交互提示。
4. 实现携带物品与合法目标检查，保证同一物品只有一个持有者。
5. 实现单个顾客生成、走向桌子、入座和自动点单。
6. 建立订单状态及通用工作接口；做菜先使用简单计时。
7. 实现取菜、上菜、用餐、自动付款和离店。
8. 实现收盘、搬到回收点及桌子重新可用。
9. 加入最小界面：金币、当前订单、携带物、交互提示。
10. 加入开发调试入口：生成顾客、重置本局、查看订单状态。

### 5.2 本阶段边界

- 食材暂时无限，不做采购、工资、评价、员工或升级。
- 只使用一种菜品，暂不做正式小游戏。
- 订单和任务仍需有明确标识，为后续多人同时工作预留结构。

### 5.3 验收标准

- 连续完成至少 10 轮接待，不需要重启场景。
- 每个订单只付款一次，反复交互不会重复生成菜品或金币。
- 手里有物品时，不能再取第二个物品。
- 收盘完成前桌子不可被新顾客使用。
- 非法交互有可理解的提示，玩家不会无故失去携带物。

**交付物：** 可运行的单人服务原型、基础状态图、已知问题清单。

## 6. 阶段二：营业压力与操作乐趣

**目标：** 从按顺序执行操作，变成需要判断工作优先级的经营体验。

### 6.1 工作清单与顺序

1. 增加到约 4 张桌子，实现桌子预留，避免顾客重复占座。
2. 增加顾客生成节奏与最大在场人数，支持低峰和高峰配置。
3. 增加订单列表、等餐耐心与即将超时提示。
4. 实现顾客超时离店，清理订单、成品和未完成任务。
5. 加入第二道菜，通过配置调整耗时、售价和外观。
6. 实现火候小游戏，并打通普通、优质、超时和取消分支。
7. 加入有限地面污渍生成、清洁交互和环境状态显示。
8. 加入评价原因：等待时间、品质、整洁度。
9. 实现营业计时、停止入店、收尾时限与基础日结页。
10. 记录订单等待时长、接待量、流失量等调试数据，调整忙碌程度。

### 6.2 设计约束

- 首轮调优先用一套固定参数，不随机叠加多个惩罚。
- 污渍数量设置上限，避免无限堆积或遮挡角色。
- 顾客离店后，对应食物显示失效并允许回收，不让玩家长期端着无效菜品。
- 评价先提供反馈，不直接引入强烈的客流惩罚，避免差评造成不可恢复的连锁失败。

### 6.3 验收标准

- 至少有两种工作同时等待，玩家能基于界面判断优先级。
- 高峰期间允许出现少量流失，但仍可以继续经营。
- 顾客在制作前、制作中、待上菜时离店，均不会留下永久占用。
- 小游戏期间能看清餐厅主要状态；超时不会锁死角色或工作台。
- 正常营业和超时收尾都能进入结算。
- 结算能说明至少一个具体问题，例如“3 位顾客因等餐超时离店”。

**交付物：** 可完整游玩一个营业日的手动经营版本、首轮节奏参数表。

## 7. 阶段三：员工自动化与共同工作

**目标：** 一名员工能持续承担工作，玩家能通过优先级设置与主动补位改善经营。

### 7.1 工作清单与顺序

1. 将阶段一、二的工作接入统一任务调度，移除角色各自修改订单的重复逻辑。
2. 实现任务领取、物品预留、工作台占用和资源释放。
3. 实现员工状态机和走向操作位置的路径规划。
4. 先实现上菜与收盘，验证搬运流程。
5. 再实现清洁和自动做菜，接入与玩家相同的任务完成结果。
6. 增加工作类型开关及优先级界面。
7. 实现简单调度规则：先按用户设置的优先级，再按紧急程度和距离选择任务。
8. 增加员工状态显示和失败原因显示。
9. 处理无效订单、路径失败、资源不足和出餐位置满等分支。
10. 使用相同客流配置，对比纯手动经营与雇员协作表现。

### 7.2 任务协作规则

- 领取成功后立刻写入执行者，不能等角色走到目标才占用。
- 员工调整工作优先级后，默认完成手头工作，再按新配置选择下一项。
- 玩家不能重复拿走已被员工预留的菜品；对应提示必须明确。
- 任务取消时，释放工作台、菜品、出餐位置等资源。
- 员工携带失效菜品时，先执行回收动作再领取新任务。
- 暂时没有工作时站在不影响操作的位置，避免反复来回走动。

### 7.3 验收标准

- 员工能分别完成四类实操工作。
- 主角和员工同时尝试领取同一任务时，只有一方成功。
- 禁用某类工作后，员工不再领取新的该类任务。
- 玩家不操作时，只要有足够食材和可用设备，员工能够完成基础服务循环。
- 以目标在场人数运行至少 3 个营业日，没有永久占用或持续空转。
- 人为设置不可达目标时，员工显示原因并尝试其他工作。
- 对比测试中，雇员至少明显减少一类重复劳动，且玩家仍有补位价值。

**交付物：** 支持一名员工的协作经营版本、任务异常处理记录、雇员体验评估。

## 8. 阶段四：经营系统、成长与存档

**目标：** 建立跨营业日的成长循环，让采购、雇佣、布局和升级产生实际影响。

### 8.1 工作清单与顺序

1. 实现食材定义、库存、预留与实际消耗。
2. 增加开店前采购界面，显示单价、购买数量、余额与可制作份数。
3. 增加菜单开关，阻止顾客点无法履约的菜品。
4. 增加雇佣入口、每日工资和停止雇佣入口；营业中不改变雇佣关系。
5. 增加账本，分开记录营业收入、食材采购、工资、设备和家具支出。
6. 实现非营业阶段的家具摆放预览、合法性检查与取消还原。
7. 实现一种烹饪设备升级，并在界面展示升级前后的效果。
8. 实现一次固定区域扩建、费用扣除和地图通行更新。
9. 实现完整日结页，显示现金变化、经营表现和主要问题。
10. 实现本地存档、读档、新游戏和基础存档版本处理。
11. 加入资金不足恢复方案，完成多日经济调优。

### 8.2 经济规则

金币变化遵循：

```text
日末现金 = 日初现金 + 实收营业收入
          - 当日采购付款 - 工资付款 - 家具设备与扩建付款
```

日结同时区分：

- **现金变化：** 实际收到和付出的金币。
- **食材消耗成本：** 当天使用食材的成本估计，用于判断菜品是否赚钱。
- **经营收益估计：** 营业收入减去消耗食材成本与工资，避免把大量囤货误认为当天经营失败。

首版使用固定采购单价即可，不实现复杂成本计价。设备与扩建单独列示，不混进菜品经营效率。

暂定调优目标：

- 第一位员工应在前几个营业日内可负担，尽早验证核心体验。
- 第一位员工的工资不能吃掉新增经营收益的全部。
- 第一次扩建应在约 30～60 分钟的熟悉后游玩内可达；这是测试目标，需按实际节奏调整。
- 不要求玩家重复同样操作很多天才能看到首次成长。
- 保留低成本基础菜和一次有限的应急补给；关闭高成本菜单后仍有恢复空间。

工资处理采用简单方案：开店时锁定当天工资所需现金，结算时支付；不足时员工当天不出勤，并在开店前提示。锁定现金不能再用于采购，避免出现隐含欠薪或负数余额。

### 8.3 存档范围与边界

- 首版仅在日结完成、场景清场之后保存，不恢复营业中途的角色和任务。
- 存储稳定标识与数值，不存储场景节点引用。
- 先写临时文件，成功后替换正式存档；保留上次有效备份。
- 缺少可选字段时使用默认值；无法读取时提示恢复备份，不静默覆盖坏档。
- 新游戏覆盖已有进度前需确认；这是游戏内用户操作保护。

### 8.4 验收标准

- 多个订单同时创建时，食材预留不会超过库存。
- 开工前取消订单释放食材；开工后取消不返还已消耗食材。
- 采购、雇佣、升级和扩建都不会重复扣款或产生负数可用现金。
- 不合法家具位置无法确认，取消布置后恢复原位置与金币。
- 扩建后角色可以到达新增区域，旧家具和订单逻辑正常。
- 从新档连续完成至少 5 个营业日，达到首次雇佣和至少一次成长目标。
- 保存并重启后，金币、库存、员工、布局、升级和扩建结果一致。
- 资金不足时存在明确可行的恢复路径。

**交付物：** 可完成首次扩店的首版功能完整版本、经济参数表、存档格式说明。

## 9. 阶段五：像素表现、引导与体验打磨

**目标：** 让未参与开发的玩家能够理解玩法，顺利完成经营与成长。

### 9.1 工作清单与顺序

1. 固定视觉规范：格子尺寸、角色比例、色板、朝向和界面字体。
2. 替换主要占位素材：场景、主角、员工、顾客、家具、菜品和污渍。
3. 增加最低必要动画：待机、移动、携带、工作、用餐和情绪反馈。
4. 统一交互提示、任务图标、不可操作原因和紧急状态颜色。
5. 加入关键音效：完成烹饪、上菜、付款、顾客离店、升级。
6. 实现渐进引导：首桌服务 → 收盘 → 结算 → 采购 → 首次雇佣。
7. 提供暂停、音量、窗口/全屏等基础设置，检查中文字体可读性。
8. 邀请少量外部玩家试玩，记录困惑点、误操作与无聊时间段。
9. 根据观察修正节奏、界面与成长成本，处理阻断问题。
10. 导出目标平台版本，在开发环境之外验证启动、输入、声音、存档和退出。

### 9.2 视觉优先级

优先保证可读性：顾客是否在等餐、哪道菜做好了、桌子是否可用、员工在干什么，必须一眼能看出来。装饰、环境动画和大量角色外观在这些信息清晰后再补充。

可暂按 16 或 32 像素格子做样例对比，最终选择一种并统一素材规范。正式素材批量制作前先完成一小块场景验证缩放和文字显示效果。

### 9.3 验收标准

- 建议邀请 3～5 位未参与开发的玩家试玩，作为发现问题的样本，不把小样本结果当成市场结论。
- 多数测试者无需开发者口头指导即可完成第一桌服务。
- 测试者能解释员工当前负责什么，以及为什么某位顾客给出差评。
- 玩家在忙碌时仍能辨认订单、可交互对象与主要风险。
- 扩建后的目标负载下无明显持续卡顿，帧率目标在确定测试设备后记录。
- 导出包能从新档运行到存档、退出、重启并读取进度。
- 阻断经营或丢失进度的问题全部修复；剩余问题有清单和处理优先级。

**交付物：** 可分发试玩版本、试玩观察记录、版本说明、后续迭代清单。

## 10. 建议排期

以下为粗略工作量估算，假设熟悉 Godot 的单人全职开发者，每周约 5 个有效开发日。包含基础实现与阶段验收，不包含大量原创美术、商业发行准备或平台审核；Godot 初学者需要额外安排学习时间。

| 阶段 | 建议工作量 | 日历参考 | 主要里程碑 |
|---|---|---|---|
| 阶段一 | 4～6 个工作日 | 第 1 周至第 2 周初 | 单桌服务闭环 |
| 阶段二 | 5～8 个工作日 | 第 2～3 周 | 完整手动营业日 |
| 阶段三 | 7～10 个工作日 | 第 3～5 周 | 员工与玩家协作 |
| 阶段四 | 8～12 个工作日 | 第 5～8 周 | 首次扩店与存档 |
| 阶段五 | 6～10 个工作日 | 第 8～10 周 | 可分发试玩版本 |
| 整体缓冲 | 5～10 个工作日 | 第 10～12 周 | 吸收异常修复与体验返工 |

总计约 **35～56 个工作日，即 7～12 个全职工作周**。日历参考会随各阶段实际耗时移动，不代表各阶段可以独立并行。兼职开发应按每周实际投入时间重新换算。

### 10.1 首周可执行安排

| 工作日 | 主要任务 | 当日可检查结果 |
|---|---|---|
| 第 1 天 | 建项目、输入、主角、占位地图 | 主角能移动并被墙阻挡 |
| 第 2 天 | 交互目标、操作位置、携带物品 | 能拿取并交付一个测试物品 |
| 第 3 天 | 顾客、桌子预留、订单 | 顾客入座后生成唯一订单 |
| 第 4 天 | 做菜、出餐、上菜、用餐付款 | 完成第一笔营业收入 |
| 第 5 天 | 收盘、桌子恢复、重复接待检查 | 连续接待多轮顾客 |
| 机动时间 | 修复状态与交互问题 | 达到阶段一全部验收标准 |

### 10.2 每周固定流程

1. 周初选择一个玩家可感知的结果，不只列底层模块名称。
2. 每天结束保留一个可运行版本，记录已知问题。
3. 周末走一遍目前完整流程，核对当前阶段验收标准。
4. 新想法先进入候选清单，除非影响当前核心体验，否则不插入本周。
5. 未通过阶段验收时优先修复，不通过增加新内容掩盖问题。

## 11. 测试与问题优先级

### 11.1 重点验证矩阵

| 场景 | 必须满足的结果 |
|---|---|
| 两名执行者同时领取同一任务 | 只允许一方成功 |
| 顾客在做菜前离店 | 取消订单，释放食材和任务预留 |
| 顾客在做菜中离店 | 已消耗食材不返还，设备和出餐位置最终释放 |
| 顾客在员工端菜途中离店 | 食物失效并被回收，员工继续工作 |
| 出餐台已满 | 不开始无法放置成品的新制作任务 |
| 所有桌子都脏了 | 停止分配座位，清理后自动恢复接待 |
| 库存不足且存在多个订单请求 | 只有有库存保障的订单被接受 |
| 玩家手持物品尝试不兼容交互 | 拒绝操作，物品与任务状态不变 |
| 员工任务目标不可达 | 不永久卡住，显示原因并重新调度 |
| 营业截止仍有未完成订单 | 在收尾规则内完成或取消，能够结算 |
| 布置堵住入口或工作台 | 阻止确认，保留原有合法布局 |
| 结算按钮被重复触发 | 不重复发放收入或支付工资 |
| 存档写入失败 | 不损坏上一份有效进度，并显示失败提示 |
| 余额不足以支付工资 | 开店前提示员工不出勤，可继续自行经营 |

订单状态、库存预留、任务唯一领取、金币记账和存档往返适合做自动化验证；操作手感、提示可读性、地图动线和小游戏体验以实际游玩检查为主。

### 11.2 问题分级

- **P0：** 无法启动、存档丢失、无法继续经营。立即修复。
- **P1：** 重复结算、资源泄漏、员工永久卡死、成长无法完成。当前阶段结束前修复。
- **P2：** 提示不清、局部操作不顺、节奏不合理。纳入最近一次体验迭代。
- **P3：** 非关键动画、装饰和表现细节。核心流程稳定后处理。

## 12. 关键风险与处理方式

| 风险 | 早期信号 | 处理方式 |
|---|---|---|
| 重复劳动太多 | 玩家觉得一直只是在收盘 | 减少重复交互，让首次雇佣更早出现 |
| 雇员之后无事可做 | 玩家长期站着等待 | 调整高峰、角色效率和分工，让补位与管理有价值 |
| 雇员收益不明显 | 雇人后流程没有改善 | 检查任务优先级、路线和工资，不急着增加员工属性 |
| 小游戏打断经营 | 玩家为了操作看不到顾客超时 | 缩短小游戏，缩小遮挡，调整压力与奖励 |
| 布局与寻路复杂 | 家具移动后频繁卡住 | 限定营业前布置，严格验证操作位置可达 |
| 状态逻辑失控 | 出现幽灵订单、重复菜品 | 明确唯一标识、状态归属和取消清理规则 |
| 成长只靠等待 | 玩家知道如何赚钱但没有新决策 | 缩短前期门槛，使升级解决不同瓶颈 |
| 内容制作拖慢进度 | 大量素材完成但无法完整营业 | 先通过阶段验收，再批量制作素材 |

## 13. 首版完成后的扩展顺序

按试玩结果选择，不默认全部制作：

1. **更多分工：** 多名员工、工作区域、简单熟练度，验证规模经营。
2. **更丰富菜单：** 菜品偏好、套餐、少量不同制作玩法。
3. **更多布局选择：** 多种设备、有限餐具循环和更丰富扩建。
4. **更强经营差异：** 不同顾客类型、口碑影响客流、活动日。
5. **长期个性化：** 装饰主题、员工外观、成就和轻量剧情。

每增加一项内容，都应回答：它让玩家做出了什么新的选择，是否能复用现有系统，以及是否增加了难以理解的重复劳动。
